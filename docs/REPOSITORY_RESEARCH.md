# Repository presentation research

Date: 2026-11-02. Goal: make CAM understandable and credible to a new visitor without overstating product readiness.

## Sources

- [GitHub repository best practices](https://docs.github.com/en/repositories/creating-and-managing-repositories/best-practices-for-repositories): explain the project, establish contributor expectations and enable appropriate security features.
- [GitHub contributor guidelines](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/setting-guidelines-for-repository-contributors): provide discoverable contribution instructions and issue/PR templates.
- [GitHub community health files](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/creating-a-default-community-health-file): use conventional supported paths for project guidance.
- [GitHub private vulnerability reporting](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository): provide a private reporting route when enabled; do not claim the setting is enabled merely because SECURITY.md exists.
- [Tauri repository](https://github.com/tauri-apps/tauri): reference for a clear introduction, documentation entry points and contribution links. CAM does not reuse its artwork or claim its verification status.

## Applied decisions

Use an original local SVG banner, real fixture-backed UI screenshots with provenance captions, concise feature/status tables, a safe quick start and a separate release-readiness checklist. Avoid external tracking badges, invented downloads/stars, fake CI success, copied third-party artwork and an assumed open-source license. Keep historical implementation notes linked but make the current status authoritative.
