# Coding Studio implementation evidence

Status: **M2 in progress**. Explorer, bounded text reads, existing/new-file proposals, exact approvals, checkpoints, selective rollback, Windows commands, Git inspection, explicit recovery, durable per-file review and approved empty projects are implemented. Live-model coding verification remains pending. Current evidence is in `M2_PROJECT_AI_REVIEW.md`; this is not the completed Coding Studio acceptance gate.

## Implemented context boundary

- Root and nested `.gitignore` rules are parsed with pinned `pathspec==0.12.1`, a small pure Python dependency; no repository hook/script is executed for context collection. Nested negation fixtures are compared against actual Git.
- Directory scans examine at most 1,000 entries. Text reads are UTF-8 and at most 64 KB; ignore files are at most 16 KB. Binary files, symlinks/junctions, excluded directories and credential filenames are rejected.
- Both `studio_read`/`studio_list` and legacy `read_file`/`list_directory` use the same handlers in selected projects. Personal workspace tools remain separate.
- Windows file reads verify the actual opened handle destination. Windows directory listing pins directory handles along the route with read access and without delete sharing until enumeration finishes. Native regression testing demonstrates that the exact pre-enumeration rename/junction swap is blocked. This is scoped inspection, not a general filesystem sandbox. [CreateFile reference](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew).
- Credential detection is shared with memory validation: quoted JSON credential fields, named short secrets, refresh tokens, private-key blocks, Bearer values, recognized token prefixes and embedded URI credentials are excluded. This conservative heuristic can reject legitimate source snippets and cannot identify every arbitrary secret. Users must not rely on content detection as their only credential protection.
- Planner instructions use the same bounded reader, and are omitted when current read policy requires approval or denies reads. Instructions cannot grant tool permissions.
- The UI renders source as text, clears prior project contents on switching, and displays the actual result of approved read continuation. It never interprets source as HTML or treats echo output as file execution.

## Existing-file checkpoint contract

Migration 3 adds project-scoped checkpoints; migration 1/2 sources remain unchanged. Upgrading an existing database still requires explicit authorization and produces a consistent backup. Only temporary databases have been upgraded during verification.

Proposals store original/proposed UTF-8 bytes, content hashes, canonical root, path and an immutable proposal hash. Apply and rollback approvals include the actual diff and before/after hashes. Stale content, another project, changed root, altered checkpoint bytes, an expired/revoked grant or a consumed/competing action cannot silently overwrite later edits. Interrupted `applying`/`rolling_back` records remain uncertain and cannot blindly retry. `studio_changes` exposes bounded checkpoint identities and states for inspection.

Native Windows writes lock the original file and preserve owner/group/DACL/creation attributes. Additional streams, sparse/compressed/encrypted files and unsupported metadata rights fail closed. No in-place fallback is used. A prepared replacement is published by moving the original handle to a managed backup, then moving the replacement into the exact destination with **no overwrite**. A hard link introduced at this final boundary keeps the original bytes. This is a **two-phase operation**, not an atomic filesystem transaction: normal failure restores the original when the destination remains absent; a later user-created file is preserved and the original managed backup is retained. A crash between phases requires checkpoint/backup inspection before recovery. Managed `.jarvis-stage-*` and `.jarvis-backup-*` files are excluded from ordinary project context. OS-specific crash recovery must pass before the full M2 release gate.

The legacy writer also uses this replacement strategy. Native regressions cover late hard links through apply, rollback and legacy overwrite; competing grants at dispatch; external writers; expiry/revocation after the durable claim; compensation between renames; preserving a later file; and retaining additional stream data. [Microsoft handle rename semantics](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fscc/4217551b-d2c0-42cb-9dc1-69a716cf6d0c).

Actual Windows UI acceptance was rerun after the copy-on-write corrections: editor → reviewed diff → separate approval → apply → separate rollback approval → verified restore passed, together with pairing, project isolation and re-pairing (12 workflow checks). Evidence files use the `m2-checkpoint` prefix. Providers remained mock; no live inference was claimed.

## Approved command integration

Migration 4 adds `command_runs`; migration sources 1/2/3 remain unchanged. Temporary v3 databases refused unapproved migration, then upgraded with a consistent v3 backup and preserved project data. No real user database was opened or migrated.

`studio_prepare_command` records the exact canonical executable, executable SHA-256, argument array, project root, working directory and timeout/output limits. `studio_run_command` requires a separate HIGH-risk COMMAND approval. The executable is opened without write/delete sharing and remains locked through execution; the directory route is pinned. An altered contract, changed binary, changed policy revision or another project is denied. Prepared commands atomically transition to running so competing approvals cannot duplicate execution. Interrupted outcomes retain an explicit non-retryable record. Approved code runs with user privileges and may access files/network outside the project; no filesystem sandbox is claimed.

Authorization uses the actual approved policy revision and one consistent snapshot for revision/category. The queue rechecks expiry, session validity, current policy and exact scope before launch. The final check follows reader-thread startup and precedes native ResumeThread. Cancellation/timeout terminate the owned process job; already-accepted external effects cannot be undone.

Nonzero exit, timeout and output overflow propagate as unsuccessful tool results with evidence. Exit code 259 is classified from the signalled process handle, not the STILL_ACTIVE constant. Late output-capture errors cannot report success; cleanup attempts all owned handles even when a termination operation reports an error. CommandPanel reviews the prepared contract, requests a separate grant, approves or rejects it, displays escaped actual output, and clears old-project state. Default UI limits are 60 seconds/64 KB. The child environment excludes arbitrary backend/session/provider variables; requested tooling may require explicit future environment support.

Independent integration review initially passed with two Low findings, then passed closure after queued expiry/revocation, active cancellation and rejection regressions. Actual Windows Edge fixture acceptance completed the approval flow, wrote proof only into the selected project, captured real output and reported exit 7 as failure; all 13 workflow checks passed. Evidence: `docs/evidence/m2-command-windows-acceptance.json`. Mock model providers were used; this demonstrates command execution, not live AI coding.

## Current retention and explicit recovery contract

Successful existing-file replacement and rollback now retain the original inode at a project-relative `.jarvis-backup-<change-id>-apply` or `-rollback` location. Created-file rollback retires its still-owned inode there instead of physically deleting it. This supersedes earlier cleanup descriptions: original versions accumulate on disk, are excluded from model context/explorer, and are never automatically purged. Coding Studio's checkpoint history exposes the possible retained locations; actual recovery inspection checks which files exist.

Interrupted operations are not blindly retried. `studio_inspect_recovery` observes the public file and the exact retained checkpoint, including opened-handle identity and content hash. `studio_recover` requires a fresh HIGH-risk approval bound to that observation. It either reconciles an already verified effect or restores a retained original into an absent public path by owned-handle rename. Changed/recreated files, stale observations, cross-project requests, additional streams and unsupported states fail closed. Such states need manual inspection; retained originals are preserved. File movement and database reconciliation remain separate operations, so recovery itself can be interrupted and require another inspection. Created-file ownership is journaled before publication.

Installed Windows Edge exercised **16 fixture workflow checks**, including real new-file creation and rollback with retained inode/byte evidence. Temporary databases/projects were removed; mock models were used. This does not establish live-model coding or complete M2 acceptance.
