# New-file checkpoints and retention

New-file proposals bind absence as part of the immutable project/root/path/content contract. Applying never replaces an existing file, including one created at the native commit boundary. The new file's device/inode identity is captured while its handle remains owned. Migration 5 stores identities as text because Windows volume identifiers can exceed SQLite's signed integer range; migrations 1–4 remain unchanged. No real user database was migrated.

Created-file rollback has a separate HIGH-risk destructive-category approval. The ordinary edit rollback cannot remove a created file. Rollback verifies the actual opened file's identity, content and streams and revalidates authorization after the final native query. Identical-content files recreated by the user are preserved.

The reviewer reproduced late alternate-stream loss and failed cancellation of pending physical deletion. The final implementation avoids physical original deletion: existing originals and removed created files are retired through owned handles into `.jarvis-backup-*` checkpoints. Original bytes, ownership metadata and streams remain available. Checkpoints are excluded from ordinary context and are not automatically purged. They consume disk space. Coding changes use deterministic retirement paths derived from the approved immutable change ID and apply/rollback phase. Interrupted records remain uncertain until explicitly inspected/recovered.

Meaningful native regression coverage includes actual late stream creation after a durable claim, creation at the final rename/query boundary, unavailable deletion APIs, later user files, identical-content replacement, separate destructive approval, synchronized competing grants, and expiry/revocation after the final stream query. Tests use temporary projects/databases only. Backend targeted verification currently passed 15 new-file tests plus existing checkpoint checks; independent targeted native/checkpoint/migration verification passed 51 tests before final documentation.

Frontend verifies new-file proposal routing, separate rollback tool, current content/hash after apply, continued edits and no continuation after unmount during approval. Seven targeted CodingStudio tests passed. Full current backend/frontend verification and new-file installed Edge acceptance are still pending after the final retirement change. Explicit recovery and multi-file changes are also pending; this is not a declaration that M2 or the whole product is complete.
