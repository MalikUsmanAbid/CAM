Tokens stay in frontend memory, not URLs, cookies or persistent browser storage. The terminal displays a replacement code after pairing and periodically refreshes it, supporting dashboard reload without backend restart. Codes are not written into the database or application logger.
- All routes except minimal health/pairing and CORS preflight require a session, including API documentation. Host, peer and Origin restrictions still apply. Authentication errors carry the allowed dashboard CORS headers; protected responses use `Cache-Control: no-store`.
- Execution approvals include session identity, project identity, action category, policy version and durable policy revision alongside exact argument, tool-contract and canonical destination hashes. A different session or changed policy/scope cannot continue an old approval. Session validity and current category policy are checked again at dispatch.
- All repository initializers share the transactional migration ledger. Existing databases refuse upgrades without explicit opt-in. Authorized migration first uses SQLite's consistent backup API, then transactional DDL. Checksums, continuous version history and complete table/column contracts reject incompatible or damaged schemas. Failures roll back the ledger and new tables.
- Registration of existing canonical project directories without scanning/modifying/transmitting project files. Drive roots are rejected; aliases reuse the registration.
- Project-scoped filesystem execution, task routing, selected memories and bounded untrusted instructions. ## Development startup changes

For a **new, empty database**, use the existing loopback backend startup command, copy the current code from its terminal, and enter it into the dashboard's pairing form. A refresh discards the in-memory token; successful pairing and periodic rotation print fresh codes without invalidating other active sessions. A private desktop bootstrap channel is deferred to M3.

For an **existing user database**, startup intentionally stops before repository initialization/recovery. Review the migration and destination `migration_backups` directory first. Only after approving that operation, set `JARVIS_ALLOW_DATABASE_MIGRATION=1` for the authorized startup. Remove the opt-in afterward. No migration of real user persistence has been performed here. Backup files contain user data and need the same filesystem protection as the original database; encrypted backup/recovery belongs to M9.
